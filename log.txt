=== DELIVERABLE 2: code/engine.py ===

Pure Python. No API calls. No LLM. Deterministic.

Build these pieces:

1. load_all() -> loads every CSV into clean dataclasses/dicts, keyed by
   user_id and request_id. Converts all foreign currency amounts to the
   user's home_currency using exchange_rates.csv matched on date +
   currency pair.

2. build_ledger(user_id, request_date) -> a clean list of dated cash
   movements for the next 90 days. This must:
   - expand recurring expenses into individual dated occurrences
   - include confirmed future salary
   - include confirmed pending payments
   - EXCLUDE pending credits, failed transactions, cancelled
     transactions, duplicate records, and unrealized/non-cash investment
     values
   - apply linked_event_id resolution: a later event in a chain
     supersedes the earlier one
   Print a readable ledger for 3 sample users so I can eyeball it.

3. simulate(user_id, request_date, extra_payments, spending_changes)
   -> returns (is_safe: bool, min_balance_hit: float, daily_balances)
   Walks day by day for 90 days from request_date. Starts at
   available_balance. Applies the ledger plus extra_payments plus the
   effect of spending_changes. Returns False if balance ever drops below
   minimum_balance_to_keep.

4. max_safe_today(user_id, request_date, requested_amount)
   -> binary search using simulate(). Largest amount payable on
   request_date that stays safe. No spending changes applied. Capped at
   requested_amount. Round consistently.

5. earliest_full_date(user_id, request_date, requested_amount)
   -> loop each of the next 90 days, return first date where paying the
   full amount as a single payment is safe. No spending changes. Return
   None if never.

CRITICAL: put every ambiguous rule behind a flag in a single CONFIG dict
at the top of engine.py. Do not hardcode a choice. At minimum:
  - salary_applied_before_expenses_same_day: True/False
  - min_balance_checked_after_payment: True/False
  - forecast_includes_day_90: True/False
  - forecast_starts_day_0_or_1
  - rounding_mode: floor / round / 2dp
  - reduce_to_uses_minimum_cut vs reduce_to_zero
Add any other ambiguity you find while reading the spec. List every flag
you created in DATA_NOTES.md with the two interpretations.

=== DELIVERABLE 3: code/evaluate.py ===

Runs the engine against dataset/sample_requests.csv and scores it.

- per-column accuracy (exact match, plus numeric tolerance for
  amount_safe_to_pay)
- overall row-exact-match percentage
- for every failing row: print request_id, my value, expected value, side
  by side, for the columns that differ

For now, generate predictions with the simplest possible logic: if
max_safe_today >= requested_amount then affordable_now + full_payment,
else not_affordable. I expect a low score. I want the harness working and
the failure list visible.
